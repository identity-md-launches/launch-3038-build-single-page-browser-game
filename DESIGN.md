# Squeekchain Tap design

## Overview

A small, playful game for the Squeekchain hamster economy. The visual idea is a warm, illustrated gold medallion in an otherwise quiet dark interface. The balance, three earnings stats, and hamster button form the main play area; three restrained upgrade surfaces form the shop. The header holds the product name and blue help button, without a separate marketing hero.

All product styles, components, SVG artwork, and game behavior live in `index.html`. The design uses system fonts and original inline SVGs. `assets/favicon.svg` is a simplified hamster mark; `assets/og-image.png` is generated by `scripts/share-card.mjs` from the same main hamster artwork. These metadata assets are local.

## Typography

Font stack: `ui-rounded, "SF Pro Rounded", system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`. No font files are downloaded. The actual face depends on the operating system's available fonts; a computed family list does not identify a specific rendered face. Weights are 400, 600, and 700.

| Token | Size at the default root | Usage |
| --- | --- | --- |
| `--text-caption` | 0.875rem / 14px | Hints, descriptions, prices, levels, footer |
| `--text-body` | 1rem / 16px | Upgrade headings, currency label, main tap instruction |
| `--text-subheading` | 1.25rem / 20px | Small-screen product title and help heading |
| `--text-heading` | 1.5rem / 24px | Larger product title, shop heading, stats, gain feedback |
| `--text-balance` | 4rem / 64px | Main balance |

Body line height is 1.5; headings and stat values use 1.2; the balance uses 1.1; stat labels use 1.45. The short gain bubble uses 1. Heading tracking is `-0.025em`, and the large balance uses `-0.045em`; other UI text has natural tracking. `.number` enables tabular numerals for every changing numeric value.

Headings use balanced wrapping; paragraphs use pretty wrapping. Critical amounts wrap instead of being abbreviated or ellipsized. The footer has a 65ch maximum measure. Text remains selectable outside the tapping button. Browser testing included 200% root-text enlargement; this is distinct from native browser zoom.

## Layout

The spacing tokens `--space-1` through `--space-12` provide 4, 8, 12, 16, 20, 24, 32, 40, and 48px steps at the default root. Reuse the existing named steps for layout. Small optical adjustments are 3px and 6px.

- `.shell`: centered, maximum width 1168px, minimum height `100svh`, flexible vertical flow. Initial inline margins are at least 20px and account for safe-area insets.
- Below 36rem: one column, full available content width, 20px product title. The shop follows the play area in DOM and visual order. Header tagline occupies its own row. Upgrade headers and action rows wrap.
- From 36rem: inline padding becomes 32px, product title becomes 24px, and the single-column game has a 560px maximum width.
- From 58rem: `.game-layout` becomes two columns. The shop is 360–440px wide; the play area uses the remaining width, with a 48px column gap and 24px end inset. The tagline moves into the header's main row. This breakpoint is 928px at default text sizing.
- `.stats`: three equal `minmax(0, 1fr)` columns; names wrap, and changing values use tabular figures. Subtle vertical separators distinguish the three metrics.
- `.coin-stage`: up to 316px in the single-column view and 336px in the desktop view, never wider than its parent. The halo expands by only 4%, containing it at 320px.
- `.upgrade-action`: wrapping flex layout. The effect and 44px buy button share a row when they fit; the button moves below at narrower sizes.

Rendered checks cover 320, 390, 768, 928, and 1440px widths. The full hamster button and product name are visible on the initial 390 × 844 screen. Content scrolls vertically, never within a clipped game pane. Header, play area, shop, and footer stay in normal document flow. Logical properties support the checked RTL mirror.

## Elevation & Depth

Upgrade surfaces use a flat fill without borders or shadows. Header/footer rules and stat separators provide structure. Available buy buttons have a border, with no shadow. The small help panel alone uses an elevation shadow, `0 16px 48px #0008`, and no border.

The hamster's bevel, fur gradients, drop shadow, ring marks, and sparkles are part of the inline SVG illustration. `.coin-stage` isolates its halo; feedback sits at local z-index 2, help at 10, and the skip link at 20. The interface has no fixed controls or overlays covering the game when help is closed.

## Shapes

`--radius-card` is 1rem / 16px, used by upgrade surfaces and the help panel. `--radius-control` is 0.625rem / 10px, used by buy buttons. Level labels use 6px corners; progress bars use 4px corners. The 44px help control and main tapping button are circular. Gain feedback is a compact, solid rounded bubble so its gold number stays legible over the illustration.

## Components

These are DOM/CSS patterns in `index.html`, not exported framework components.

| Pattern | Reuse and behavior |
| --- | --- |
| `.brand`, `.site-header` | One product `h1`, original 32px hamster mark, exact tagline, help utility at the trailing edge |
| `.help-toggle`, `.help-panel` | Native disclosure button with expanded state and associated nonmodal panel. Toggle, Escape, outside pointer press, and outside focus close it; Escape restores the trigger's focus. No modal focus trap is needed. |
| `.balance`, `.stats` | Labeled balance group and semantic definition list. Live values come from `render()`. No fake balances or seeded players. |
| `.coin-button`, `#hamster-art` | Native button with an accessible action name; touch, pointer, Space, and Enter use the same click handler. The medallion remains the primary visual action. |
| `.tap-gain`, `#earn-status` | Actual earned amount in a decorative feedback bubble. Maximum 16 concurrent bubbles; one static bubble under reduced motion. A separate polite status announces the balance 600ms after tapping pauses. Passive mining does not announce every tick. |
| `.upgrade` | Icon, `h3`, blue level, exact description, base benefit, buy button, and native labeled progress element. Three instances use the same pattern. |
| `.buy-button` | Native disabled state below the price; available state uses warm text, neutral dark fill, and outline. Spending immediately recalculates the next price. When a focused purchase becomes disabled, focus returns to the hamster without scrolling. |
| `#shop-status` | Persistent polite purchase feedback; short messages keep the shop in place at the tested desktop breakpoint. |
| `.session-note`, `.site-footer` | Clear memory-only progress disclosure and exact game-only disclaimer |

All keyboard actions retain a 3px focus outline with a 5px offset. Forced colors uses the system `Highlight` color. With no motion preference, press feedback scales to exactly `0.96` over 100ms using `cubic-bezier(0.2, 0, 0, 1)`; hover/secondary-control colors transition within 120ms, and gain feedback floats once for 680ms. Motion is opt-in under `prefers-reduced-motion: no-preference`; there is no automatic looping motion or entrance sequence.

`prefersReducedMotion()` reads the current media query on each tap, so the JavaScript effect count and lifetime follow a changed preference as well as the CSS. Both preference-change directions were validated in Chromium and WebKit. The final rendered gain/background pair is 10.45:1; the rest of the measured color pairs and the unperformed manual checks are in `artifacts/validation.md`.

Unavailable purchases are an ordinary empty state: the price, benefit, and progress remain visible. There are no network, signing, loading, or server-error states because the game does not perform those operations. The `noscript` message explains how to enable gameplay.

## Do's and Don'ts

- Start from `.shell` and the existing spacing and semantic color tokens. Preserve the small type scale and tabular numbers.
- Keep the hamster action, real balance, and earnings stats before the shop on phones. Put instructions beside the control they explain.
- Reuse `.upgrade` and its native button/progress structure for equivalent upgrades; keep effect, price, affordability, and level synchronized.
- Preserve reduced-motion behavior, visible focus, and a keyboard path for every action. Keep decorative SVGs out of the accessibility tree.
- Preserve the requested term **Squeeks**, exact upgrade descriptions, tagline, and disclaimer.
- Keep game state in memory and the delivered page self-contained. External fonts, images, APIs, wallet code, storage, or a separate marketing hero would change this product's constraints.

A related page should reuse the shell, header, tokens, heading scale, and footer. It should state its own task plainly and use the existing control patterns where they apply; the game's two-column arrangement is not a mandatory layout for unrelated content.
